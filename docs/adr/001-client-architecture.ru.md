# ADR-001: Архитектура клиентов Atrium — монорепа, дизайн-система Atrium Flow и общий «Свой сервер»

**Статус:** Принято, выполнено (ветка `onboarding`, 2026-10-22)
**Дата:** 2026-10-21
**Решают:** владелец проекта (networkfreedom)

[English version](001-client-architecture.md)

## Контекст

Atrium — self-hosted аналог Discord для своей компании. Сервер (FastAPI + SQLite, LiveKit, Caddy) ставится одной командой
на VPS с 1 ГБ памяти. Клиенты:
- **web:** React, HeroUI v3, Tailwind v4, Vite;
- **mobile:** Expo SDK 58, React Native;
- **desktop:** Electron — оболочка над веб-клиентом плюс локальные окна на ванильном HTML/JS.

Команда — владелец и ИИ-ассистент.

**Что произошло.** Появился новый визуальный язык (DESIGN.md: OLED-чёрный, шрифт вместо плашек, шкала прогресса по краю
экрана) и сценарий «Свой сервер» на трёх платформах. Сейчас:
- **Слой Flow реализован трижды и по-разному.**
  - Три реализации: `web/src/ui/flow/` (React DOM), `mobile/src/components/Flow.tsx` (React Native), ручной DOM в `desktop/onboarding.js` (около 700 строк).
  - API разъехался: `onClick`/`onPress`, `aside` только на мобилке, `FlowPrimary` только в вебе.
  - Геометрия шкалы скопирована трижды, в компонентах остались зашитые цвета.
- **Логика «Своего сервера» продублирована** между `mobile/app/own.tsx` и `desktop/onboarding.js`: разные валидации, разные шкалы заполнения, свои копии списка задач, моков, `TURN_NAMES`. Шаги первого запуска дублируются с `web/src/account/SetupWizard.tsx`.
- **Нет инфраструктуры.**
  - Нет корневого `package.json`, линтера, автотестов веба.
  - Код между пакетами ходит через `../../web/src` и копирующие скрипты.
  - CI только собирает Docker-образы на релиз.

**Силы:**
- Внешний разработчик должен увидеть в коде обычную инженерную структуру, а не вайбкод.
- Маленькая команда: нужна простота и минимум инфраструктуры.
- Продукт должен оставаться лёгким: никаких новых серверных процессов.
- Сборки приложений сейчас работают: Docker-образ веба, dev-клиент Expo, electron-builder. Их нельзя сломать надолго.

**Как это решают проекты того же класса:**
- **Coinbase CDS:** монорепа на воркспейсах, пакеты `cds-common` (токены, типы, хуки), `cds-web` и `cds-mobile`, Storybook и демо на Expo.
- **Discord:** общая логика стора между вебом и React Native, дизайн-система Mana на всех платформах.
- **Bluesky, Expensify:** одна кодовая база на React Native плюс react-native-web, Electron — обёртка.
- **Expo:** официально поддерживает воркспейсы с SDK 52.

## Решение

**Монорепа на npm-воркспейсах с дизайн-системой по схеме Coinbase CDS и общей доменной логикой по схеме Discord.**

```
package.json            workspaces: packages/*, web, mobile, desktop; общие скрипты; ESLint
packages/ui-common      @atrium/ui-common — токены (+tokenCss), геометрия шкалы/углов/отступов, контракт пропсов
packages/ui-web         @atrium/ui-web — React DOM-реализация Flow + flow.css, Storybook
packages/ui-native      @atrium/ui-native — React Native-реализация, те же имена и пропсы, экран-каталог
packages/setup          @atrium/setup — «Свой сервер» и первый запуск без UI: шаги, шкала, валидации, задачи,
                        вместимость, интерфейс Backend, единый мок
web/ mobile/ desktop/   приложения на прежних местах; desktop/ui — окна на React (Vite) поверх ui-web и setup
```

**Правила:**
- Пакеты экспортируют только через свой `index.ts`.
- Зависимости идут вниз: `ui-common` ← `ui-web`/`ui-native` ← приложения; `setup` ← приложения.
- Границы проверяет ESLint (`eslint-plugin-boundaries`, запрет глубоких импортов и литералов цветов в слое Flow).
- Транспорт «Своего сервера» остаётся платформенным: SSH-модуль на телефоне, IPC Electron на десктопе. Модель шагов одна.
- Сервер остаётся модульным монолитом.

## Рассмотренные варианты

### Вариант A: воркспейсы + пакеты по схеме CDS (выбран)

| Измерение | Оценка |
|---|---|
| Сложность | Средняя: корневой `package.json`, правка Dockerfile и Metro, 4 пакета |
| Цена | 5–7 этапов, по коммиту на каждый; без простоя сборок |
| Масштабируемость | Новые экраны и окна собираются из готовых частей; новые платформенные пакеты добавляются тем же способом |
| Знакомость | Стандартная схема (Expo, Coinbase, Nx/Turborepo), понятная любому фронтенд-разработчику |

**Плюсы:**
- Одна дизайн-система с контрактом.
- Одна логика «Своего сервера».
- Стандартный импорт по имени пакета.
- Витрины компонентов, тесты, CI.
- Десктопные окна перестают быть ручным DOM.

**Минусы:**
- Переходный период с правкой конфигов трёх приложений.
- Корневой lock-файл.
- В десктопе появляется шаг сборки (Vite) и около 150 КБ React в локальных окнах.

### Вариант B: пакеты без воркспейсов, на алиасах путей

| Измерение | Оценка |
|---|---|
| Сложность | Низкая на старте: `tsconfig.paths` и алиасы Vite/Metro |
| Цена | Дешевле на этап |
| Масштабируемость | Хуже: у пакетов нет своих зависимостей и версий, алиасы надо поддерживать в 3–4 конфигах |
| Знакомость | Встречается, но выглядит как обходной путь |

**Плюсы:** не трогает установку зависимостей и Docker.

**Минусы:** пакеты на деле остаются папками без `package.json`. Это именно то, к чему придерётся разработчик.

### Вариант C: одна кодовая база на React Native + react-native-web (как Bluesky, Expensify)

| Измерение | Оценка |
|---|---|
| Сложность | Высокая |
| Цена | Переписать весь веб (HeroUI, Tailwind, звонки LiveKit в браузере) — месяцы работы |
| Масштабируемость | Максимальное переиспользование после переезда |
| Знакомость | Сильно меняет стек веба |

**Плюсы:** один UI-код на все платформы.

**Минусы:**
- Огромная миграция без пользы для продукта сейчас.
- Веб теряет HeroUI.
- Риск регрессий в звонках и демонстрации экрана.

### Вариант D: полный переезд приложений на FSD

| Измерение | Оценка |
|---|---|
| Сложность | Высокая: перестановка сотен файлов |
| Цена | Большая, без видимого результата для пользователя |
| Масштабируемость | Помогает большим командам внутри одного приложения |
| Знакомость | Популярна в русскоязычном фронтенде, в бигтехе клиентов этого класса не встречается |

**Плюсы:** формальная раскладка слоёв внутри приложения.

**Минусы:** не решает дублирование между платформами. Главную пользу (границы, публичные API) даёт ESLint из варианта A.

### Вариант E: микросервисы

| Измерение | Оценка |
|---|---|
| Сложность | Очень высокая |
| Цена | Больше процессов и памяти на VPS с 1 ГБ, сложнее деплой и наблюдаемость |
| Масштабируемость | Нужна для сотен команд с независимыми деплоями, не для нас |
| Знакомость | Против принципа «одна команда, 120 МБ» |

**Плюсы:** нет для нашего масштаба.

**Минусы:** прямо противоречат продукту. Проблема вообще клиентская, а не серверная.

## Анализ компромиссов

- **A против B.** Воркспейсы стоят одного этапа правки конфигов, но дают настоящие пакеты: свои зависимости, имя, `index.ts`, тесты. Expo поддерживает их официально, поэтому главный риск (Metro в монорепе) снят. B экономит день, но оставляет «папки, притворяющиеся пакетами».
- **A против C.** C даёт больше переиспользования, но требует переписать рабочий веб. A даёт общий дизайн и общую логику, оставляя каждой платформе её родной UI-стек. Это то, что сделали Coinbase и Discord.
- **A против D.** Границы и публичные API — суть FSD — получаем линтером без перестановки файлов. Внутреннюю раскладку приложений можно постепенно приводить к слоям позже, если вырастет команда.
- **E** вне рассмотрения: проблема клиентская, а сервер уже правильно устроен как модульный монолит.

## Последствия

**Становится проще:**
- Новый экран или окно собирается из `@atrium/ui-*` с одинаковым API.
- Правка шкалы, токена или валидации делается в одном месте и попадает на все платформы.
- Внешний разработчик видит стандартную монорепу, витрины, тесты и CI.
- Десктопный «Свой сервер» получает те же возможности, что мобильный: моки, ускорение, общая шкала.

**Становится сложнее:**
- Установка зависимостей теперь из корня.
- Сборка Docker-образа веба копирует `packages/`.
- В десктопе появляется шаг `vite build`.
- Контракт компонентов надо поддерживать в двух реализациях: это проверяет тест паритета.

**Вернуться позже:**
- Turborepo или Nx для кеша задач, когда сборки станут долгими.
- Перенос остальных десктопных окон (address, picker, unreachable) на `desktop/ui`.
- Общий пакет `@atrium/protocol` для типов и словарей, которые мобилка сейчас берёт из `web/src`.
- Публикация Storybook вместе с DESIGN.md.

## Как вышло

Все восемь задач выполнены, по коммиту на каждую. Отличия от плана:

- **Node 24.3+ и npm 11.** npm 10.8 падает на дереве воркспейсов (`edgesOut`), поэтому корневой `package.json` задаёт
  `engines` и `packageManager`, Docker-сборка веба идёт на `node:24-slim`.
- **`RecoveryKeyStep` остался в мобилке.** Это экран с буфером обмена и системным «Поделиться», а не часть дизайн-системы.
- **Строки частей идут через `FlowProvider`.** Пакеты не импортируют код приложений: подпись «Назад» приходит из
  приложения, `Drum` получает готовые строки.
- **Границы проверяют два правила.** `eslint-plugin-boundaries` ловит переходы по путям, а импорт по имени пакета он
  считает внешним, поэтому направление по именам задаёт `no-restricted-imports`. Он же держит `@atrium/setup` без React.
- **Главный процесс десктопа (`server-setup.js`) не тронут.** Он вне воркспейсов, его транспорт (SSH, deSEC) остаётся
  своим. Общая модель шагов работает в окне (`desktop/ui`).
- **Контракт пополнился** `KeptRow`, `Drum`, `FlowProvider` и слотом `trailing` у `LineField` (глаз пароля).

Где что лежит:
- контракт: `packages/ui-common/src/contract.ts`;
- витрины: Storybook (`npm run storybook`) и `/design` в dev-сборке мобилки;
- проверки: `npm run check` и `.github/workflows/checks.yml`.
