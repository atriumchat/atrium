## P1

### R01 Завершение звонка зависит от отправки статистики

[web/src/voice/voice.ts:226](/Users/milkzee/coding/gomex-seed/web/src/voice/voice.ts:226)

При нажатии «Положить трубку» `resetVoice()` немедленно показывает состояние `idle`, затем `leaveVoice()` ждёт `reporter.stop()`. Реальное `room.disconnect()` вызывается только после этого ожидания. У HTTP-запроса статистики нет таймаута: при зависшем запросе интерфейс скрывает звонок, а отключение комнаты ещё не произошло. Микрофон и показ экрана могут продолжать передачу до завершения запроса.

В браузерном стенде: `ui="idle"`, `roomInStore=null`, `disconnectCalls=0` при ожидающем отчёте; после разрешения запроса `disconnectCalls=1`. SDK комнаты заменён моделью, реальная передача звука не выполнялась.

Исправление: остановить локальные треки и отключить комнату независимо от статистики; отправлять статистику с ограничением времени, не блокируя завершение звонка.

### R02 Глобальная кнопка разговора включает микрофон при наборе сообщения

[web/src/voice/ptt.ts:53](/Users/milkzee/coding/gomex-seed/web/src/voice/ptt.ts:53)

Страничный обработчик игнорирует печатную PTT-клавишу внутри `input` и `textarea`. Обработчик Electron bridge вызывает `setPtt(down)` напрямую и обходит эту проверку. Если назначить `V` или пробел, набор сообщения этой клавишей включает передачу микрофона.

Воспроизведение с реальным клиентским обработчиком и моделью IPC: фокус `TEXTAREA`, `pttDown=true`, вызов `setMicrophoneEnabled(true)`. Нативный keyboard hook не запускался.

Исправление: применять ту же проверку редактируемого поля к событиям bridge, когда окно Gomex имеет фокус. Функциональные клавиши и кнопки мыши могут сохранять прежнее поведение; отпускание клавиши должно обрабатываться всегда.

### R03 Вход со старым паролем получает действующий токен после сброса

[server/gomex/users.py:253](/Users/milkzee/coding/gomex-seed/server/gomex/users.py:253)

`login()` считывает старый хеш и проверяет его асинхронно. Пока запрос приостановлен, другой запрос может сбросить пароль и повысить `token_version`. После возобновления `login()` не проверяет актуальность прочитанной записи: `issue_token()` считывает уже новую версию и выдаёт действующий токен по старому паролю. При миграции устаревшего хеша также возможна обратная запись старого пароля.

Воспроизведение: проверка старого пароля → сброс через `/api/reset` → завершение входа. Вход возвращает `200`, его токен получает `200` на `/api/bootstrap` после сброса.

Исправление: связывать проверку пароля и выдаваемую версию с одной актуальной записью; повторно проверять исходный хеш и версию, условно обновлять устаревший хеш и не подписывать результат произвольно прочитанной новой версией.

### R04 Одноразовый ключ восстановления принимается двумя параллельными запросами

[server/gomex/users.py:459](/Users/milkzee/coding/gomex-seed/server/gomex/users.py:459)

Два запроса `/api/recover` считывают один `recovery_hash`, оба проходят проверку и затем безусловно обновляют запись по `id`. Второй запрос перезаписывает пароль и новый ключ, которые только что получил первый пользователь.

Воспроизведение: оба запроса с одним ключом возвращают `200`; один из выданных токенов уже получает `401`. Для детерминированного порядка добавлен барьер после реальной проверки scrypt; БД и хеширование настоящие.

Исправление: атомарное условное обновление по исходным `recovery_hash` и `token_version` с проверкой числа изменённых строк. Только один запрос должен успешно использовать ключ.

### R05 Блокировка пользователя не запрещает получить токен личного звонка

[server/gomex/realtime.py:498](/Users/milkzee/coding/gomex-seed/server/gomex/realtime.py:498)

Socket.IO-событие `voice:join` проверяет `blocked_between`, а HTTP `/api/voice-token` проверяет только членство в DM. После блокировки собеседник всё равно получает подписанный `roomJoin`-токен комнаты личного звонка примерно на шесть часов.

Воспроизведение: создать DM → заблокировать участника → запросить токен от его имени. Ответ `200`; подпись и grant комнаты успешно проверены. Подключение к настоящему LiveKit не выполнялось.

Исправление: использовать единую проверку доступа к звонку в выдаче токена и в Socket.IO. Определить и реализовать поведение уже начатого звонка при блокировке.

### R06 Отзыв сессий приложения не завершает доступ к LiveKit

[server/gomex/realtime.py:469](/Users/milkzee/coding/gomex-seed/server/gomex/realtime.py:469)

Смена пароля, восстановление и `/api/logout-all` вызывают `disconnect_user()`, который отключает только Socket.IO. Обработчик `disconnect` удаляет присутствие из памяти, но не вызывает уже имеющийся `livekit_remove`. Независимо выданный JWT LiveKit не связан с `token_version` приложения.

Воспроизведение с моделью активной Socket.IO-сессии: после `/api/logout-all` API-токен получает `401`, JWT комнаты остаётся подписанным и непросроченным, вызовов удаления участника из LiveKit — ноль. Таким образом приложение не отправляет медиасерверу команду завершить отозванную сессию. Реальный медиасервер в проверке не участвовал.

Исправление: при отзыве доступа явно завершать медиасессии; отдельно решить срок жизни и отзыв ранее выданных токенов. Простое закрытие управляющего сокета не обеспечивает отзыв доступа к медиакомнате.

### R07 Повторный вход другого пользователя сохраняет приватный кеш прежнего аккаунта

[web/src/store/account.ts:28](/Users/milkzee/coding/gomex-seed/web/src/store/account.ts:28)

После `connect_error` с `unauthorized` приложение показывает логин без перезагрузки. Новый успешный вход вызывает `initStore()`, который меняет `me`, но не очищает `dms`, `messages`, `hasMore`, текущий DM и состояние звонка. До успешного обновления DM новый аккаунт может получить прежнюю открытую переписку из памяти. При сбое запроса обновления прежний список сохраняется. Обычный выход через кнопку делает reload и этим сценарием не затрагивается.

В браузерном стенде после `initStore()` для B: `me="B"`, но `dms=["private-A"]`, кеш сообщений и `homeView="private-A"` остались от A. Проверен переход состояния, а не полный UI-сценарий повторного логина.

Исправление: при завершении сессии и смене идентичности очищать весь пользовательский store, останавливать звонок и сбрасывать модульные кеши, включая кеш персонального приглашения.

### R08 Установщик сообщает об успешном шаге после ошибки копирования

[deploy/install.sh:1100](/Users/milkzee/coding/gomex-seed/deploy/install.sh:1100)

`run()` вызывает shell-функции в конструкции `"$fn" ... || rc=$?`. В таком контексте `errexit` не прерывает выполнение внутри вызванной функции. В частности, в `step_files()` ошибки `install` могут быть скрыты завершающим `return 0`. При сбое диска или прав установщик способен продолжить работу со старыми, отсутствующими или частично заменёнными файлами.

Воспроизведение на извлечённых из исходника `run` и `step_files`: команда `install` возвращает ошибку, файлов назначения — ноль, но напечатано `STEP_REPORTED_SUCCESS`, итоговый код — `0`. Все пути теста временные.

Исправление: явно обрабатывать ошибки обязательных команд во всех шагах. Проверить также firewall, SSH и конфигурацию; наличие `set -e` в начале скрипта здесь недостаточно.

### R10 Пагинация пропускает сообщения с одинаковым временем

[server/gomex/channels.py:255](/Users/milkzee/coding/gomex-seed/server/gomex/channels.py:255), [server/gomex/dms.py:229](/Users/milkzee/coding/gomex-seed/server/gomex/dms.py:229)

История сортируется и ограничивается только по `created_at`, следующий запрос использует строгое `created_at < before`. Если граница страницы проходит между двумя сообщениями одной миллисекунды, одно из них исключается из обеих страниц. Аналогичная схема курсора есть у inbox.

Воспроизведение в SQLite и HTTP: 51 запись, две с одинаковым временем у границы; первая страница содержит 50 сообщений, следующая — ноль. Одно сообщение недоступно при прокрутке.

Исправление: стабильная сортировка и составной курсор `(created_at, id)`, одинаковый на сервере и клиенте.

### R11 После переподключения остаются сообщения, удалённые в конце истории

[web/src/chat/history.ts:56](/Users/milkzee/coding/gomex-seed/web/src/chat/history.ts:56)

`refreshNewest()` сохраняет любое сообщение новее последнего сообщения полученной страницы, предполагая, что оно пришло по сокету во время запроса. Это также сохраняет уже известные сообщения, удалённые на другом устройстве, пока клиент был отключён.

Воспроизведение: кеш `[kept, deleted-offline]`, сервер возвращает только `[kept]`; после обновления кеш по-прежнему содержит оба сообщения.

Исправление: отличать новые поступления во время запроса через уже собранный `known`; удалённые известные сообщения за новой границей не сохранять. При неполной странице согласовывать также начало истории и `hasMore`.

### R12 Переподключение игнорирует актуальные каналы и профили

[web/src/socket.ts:132](/Users/milkzee/coding/gomex-seed/web/src/socket.ts:132)

`catchUp()` получает полный `/api/bootstrap`, но применяет только `unread` и `mentions`. Каналы, пользователи, настройки сервера, блокировки и статусы, изменённые во время отсутствия соединения, остаются устаревшими. При `connect` сервер присылает присутствие и звонки, а не полный снимок этих данных.

Воспроизведение: bootstrap возвращает новый канал, новое имя и блокировку; после `catchUp()` остаются старый канал, старое имя и пустой список блокировок.

Исправление: после reconnect согласовывать полный разрешённый серверный снимок, сохраняя локальное состояние интерфейса только там, где оно ещё допустимо.

### R13 Проверка связи зависает при ошибке получения токена

[web/src/voice/ConnectionCheck.tsx:25](/Users/milkzee/coding/gomex-seed/web/src/voice/ConnectionCheck.tsx:25)

`api.checkToken()` вызывается до `try`. При сетевой ошибке или `401` функция `attempt()` отклоняет Promise вместо возвращения `{state:"fail"}`. Её вызывающий эффект не перехватывает ошибку: проверка остаётся в состоянии `run`, callback завершения не вызывается, кнопка повторной проверки остаётся занятой.

Воспроизведение: модель `api.checkToken()` отклоняет запрос; `attempt(false)` также отклоняется с `simulated network failure`.

Исправление: охватить обработкой ошибок получение токена и создание комнаты; гарантировать завершение состояния busy при любом результате.

### R14 Бэкап БД и медиа не имеет общей точки согласованности

[deploy/backup.sh:31](/Users/milkzee/coding/gomex-seed/deploy/backup.sh:31)

Сначала сохраняется SQLite, затем отдельной операцией копируются файлы. Удаление сообщения между этими этапами может удалить его вложение с диска, хотя в снимке БД оно ещё есть. После восстановления сообщение вернётся со сломанным вложением.

Воспроизведение на временном дереве: транспорт Docker заменён локальным выполнением backup API SQLite; сразу после снимка моделируется удаление сообщения и файла. Скрипт заканчивается с `backup ok`, код `0`; снимок ссылается на `fixture.bin`, которого нет в media. Адаптированы только пути, транспорт Docker и формат времени для macOS.

Исправление: обеспечить согласованный снимок БД и медиа — например, координировать физическое удаление файлов с бэкапом либо использовать общую snapshot-процедуру. Завершённость копии следует публиковать только после проверки.

### R15 Потеря SSH после авторизации оставляет мастер без обработки ошибки

[desktop/server-setup.js:108](/Users/milkzee/coding/gomex-seed/desktop/server-setup.js:108), [desktop/onboarding.js:305](/Users/milkzee/coding/gomex-seed/desktop/onboarding.js:305)

Исправление: закрывать неуспешное соединение и возвращать структурированную ошибку из main process; дополнительно гарантировать сброс busy и показ ошибки в renderer. Аналогичные границы нужны вызову установки.
